# 段落骨架：第几段讲什么

第 4 步用这份。它把「第一段讲什么、第二段讲什么」写到能直接填空的程度。

每段给三样：**这段要回答读者的哪个问题**、**第一句写什么**、**不许出现什么**。骨架里的 `{{ }}` 是要替换的占位符，交稿时不能留着。

## 零、标题不是固定的

骨架里的 `## {{ }}` 全是占位符。每节的二级标题按 `SKILL.md` 第 4 节「标题怎么定」生成：**一段的标题 = 这一段里读者要做的事，改成动宾短语**。第三段的标题直接取六行结论里的「他第一件事」。

下面是几个第三段标题的例子。是例子，不是候选清单，不许从里面挑一个凑数：

| 读者第一件事 | 第三段叫什么 |
| --- | --- |
| 把扩展装进浏览器 | 安装 |
| 点开在线地址开始读 | 打开它 |
| 复制一行 `uses:` 接进工作流 | 接进工作流 |
| 看一段调用代码 | 用法 |
| 挑一章开始学 | 从哪开始 |

推不出来，回第 3 步重做，不许随便起名。同一个位置在不同项目里就该叫不同名字；六套骨架的标题不该长得一样。

## 一、通用六段（默认）

类别拿不准、或者判为表外情况时用这一套。

| 段 | 回答读者的哪个问题 | 第一句写什么 | 不许出现 |
| --- | --- | --- | --- |
| 1 | 这是什么，关我什么事 | 「{{项目名}} 用来 {{完成哪件事}}」 | 技术栈清单、全部平台、实现原理、连续三句形容词 |
| 2 | 凭什么信 | 图注或一句「下面这条命令的输出是 ___」 | 装饰图、Logo、和项目无关的示意图 |
| 3 | 我第一步做什么 | 「{{动作}}：」后面紧跟一条命令或一个链接 | 「按官方说明安装」「放到相应目录」这类没说完的话 |
| 4 | 做完第一步，看到什么 | 「跑一下：」后面跟最小任务和成功标志 | 完整参数表、需要额外三样准备才跑得起来的例子 |
| 5 | 除了第一步，还能提供什么 | 「{{能力名}}。{{一句短话}}」 | 写使用场景、操作步骤、实现原理；罗列技术名词 |
| 6 | 什么情况该用，接下来去哪 | 「适合 {{谁}} {{做什么}}。」 | 长句、倒装句；藏进折叠里的权限、费用、数据风险 |

## 七、每段通用的写法

- **第一段**：一到两句普通正文，不整段加粗。已有 Logo 是身份材料，不再造一个重复的大标题。信任标记（版本、持续集成、许可证）放这一段，两到七个，每个都要能帮读者判断。
- **第二段**：只放一份主证据，不把所有截图堆在开头。图注说明「这是什么、看什么」，替代文本写出图里的内容。
- **第三段**：一个能复制或点开的动作，写明执行位置和前提；不加会被误复制的 `$` 提示符；输入和输出分开。
- **第四段**：最小任务加看得见的成功标志。这是读者判断「值不值得继续」的地方，别放参数表。
- **第五段**：列产品提供的能力。一个能力一条，名称开头，后面最多一句短话。不写场景句，不写操作步骤，不写原理。
- **标题**：按 `SKILL.md` 第 4 节从「读者要做的事」推出来。不许把这份骨架或别的 README 里的标题照抄过去。
- **全篇**：短句、主谓宾、不倒装。一句话能说完的不写两句。实现方式、内部机制、数据出处整段删掉，需要时只留一个 `docs/` 链接。句子规矩见 `SKILL.md` 第 6 节。
- **第六段**：限制写在相关动作前面，不藏进折叠；没有内容就省略，不造贡献流程、路线图或文档站。

## 八、什么时候可以改顺序

| 情况 | 怎么改 | 要在六行结论里写吗 |
| --- | --- | --- |
| 视觉产品，界面一眼就懂 | 第二段紧跟第一段，甚至可以合并 | 要 |
| 研究项目，读者先看能不能复现 | 把复现条件提到第二段 | 要 |
| 很短的库，调用示例就是最好的介绍 | 用调用示例开场，第一段压成一句 | 要 |
| 某一段确实没有内容 | 整段删掉 | 要，写「删了哪段、为什么」 |
| 写着写着觉得另一套更好 | 先回去改六行结论，再改文档 | 要 |

**不许**在正文写完之后，悄悄把顺序改成另一套而不改结论——那样六行结论就失去了核对的作用，下一次也查不出当初为什么这么排。

## 九、常见错法

| 症状 | 原因 | 怎么改 |
| --- | --- | --- |
| 六段齐全，但每段都空泛 | 把骨架当成填空模板，没用第 1 步读出来的事实 | 每段至少有一个具体名词来自项目文件 |
| 第三段出现「按官方说明安装」 | 没核实安装渠道 | 查发布物或包管理配置，写出一条真命令 |
| 第二段是 Logo 或视频封面 | 把「有图」当成「有证据」 | 换成能说明区别的输出或界面 |
| 第五段写成使用场景或操作步骤 | 把「功能」理解成读者的动作 | 换成产品提供的能力，一条一句短话 |
| 交稿还留着 `{{ }}` | 没做最后一遍扫读 | 全文搜 `{{`，清零再交 |
| 通篇长句，还在讲实现原理 | 没守 `SKILL.md` 第 6 节 | 长句拆短，原理段删掉 |
