# 验收：这篇首页能不能用

判断标准是读者能否据此决定要不要试、并完成第一次使用。章节齐全、字数变少、链接全部通过、模型自评高分，都不能单独证明写得好。

## 怎么用这张清单

- 按编号顺序逐条回答，不许跳。
- 每条必须给证据：行号、引用原文、命令输出或文件路径。只写「已检查」「已符合」不算过。
- 不过的先改稿，再走下一条；确实不适用的写原因，不能拿「不适用」逃掉该做的条目。
- 交付时附报告表。缺表按未完成算，不按「基本做完」算。

报告表长这样，一行一条：

| 编号 | 结果 | 证据 |
| --- | --- | --- |
| C3 | 过 | 第 1 行标题，第 3 行徽章，第 6 行定位，第 11 行图 |
| C11 | 不过，已改 | 版本 22.20 在仓库里查不到出处，补了 `package.json` 的 `>=22.20.0` |

口径以 SKILL.md 为准。本页只列检查项和证据要求，不重复那里的数字与规则。

## A 形态与范围

**C1 形态判对了**（§1）

路由页、中间态、手册三选一，判据是有没有独立文档站或仓库内文档目录，不是正文里恰好有没有链接。

证据：写出判定，并列出仓库里支持这个判定的路径。

**C2 范围和语言都在授权内**（§2）

只改说好的范围；不改产品、许可、发布渠道或远端状态。

证据：改了哪些文件；为什么是这几版语言。

## B 首屏

**C3 四件套齐**（§4）

身份、一句定位、信任标记、第一次结果，缺一件就不过。

证据：四件各在第几行。

**C4 长度没超**（§4）

首屏控制在规定行数内。

证据：脚本报的首屏行数，不自己数。

**C5 第一次结果是读者想要的**（§5）

照这一步做完拿到的东西，是他本来就需要的结果，不是「能跑」的证明。

证据：引一句，说明这步做完拿到什么，为什么读者本来要这个。`hello world`、版本号、`--help` 输出都算没过。

**C6 信任标记有用**（§4）

徽章不超过上限，每个都能帮判断；一个都没有时用出处或赞助信息顶上，不是纯装饰墙。

证据：逐个说这个徽章让读者知道什么。

**C7 图注只说看什么**（§4、§6）

图注说明这是什么、该看哪里，不替读者下结论，也不用否定句补救。

证据：引用图注原文。

## C 内容与证据

**C8 主证据对得上交付物**（§5）

按交付物选证据，一份主证据放在首屏附近，其余按功能分置。

证据：主证据是什么、在第几行、能证明到什么程度。

**C9 诊断没进正文**（§8）

脚本输出、检查清单、修改记录、写作说明是修稿用的输入。读者要看的是成品。

证据：`check-text.py` 的输出行检查零命中；再搜 `检查`、`已修改`、`诊断`、`修复了` 这类叙述，确认没把修稿过程写进去。

**C10 差异是两种做法的对照**（§5）

写成以前怎么干、现在怎么干，不用「更快、更优雅」这类比较级；引用的数字带环境说明和出处。

证据：引用那一段。

**C11 写了什么时候别用它**（§5）

不适用场景、平台与权限限制、成熟度，至少一句。全篇只夸按未完成算。

证据：行号加原文。

**C12 事实都有出处**（§3）

版本、命令、平台、许可、下载量，都能在仓库文件或官方文档里对上。

证据：脚本的版本核对结果，加上逐条对应关系。

**C13 没有仓库文件清单**（§5、§6）

没有「目录」「仓库结构」「项目结构」这类 H2，也没有文件树和逐文件说明。文档入口同样不逐文件列名字加说明：列三份以上、每份配一句「它在讲什么」，就是换了个标题的文件清单。

有「开发」「贡献」「Development」这类 H2 时，看它展开到什么程度：只给 `CONTRIBUTING.md` 或 `docs/` 的入口算过，写进跑哪个脚本、装哪些依赖、改哪个文件、退出码怎么读就不过——那是贡献指南的内容。

证据：列出全部 H2；有文档或开发类章节时，引原文说明它给的是入口还是清单。

**C14 章节名在词表内**（§6）

H2 只用通用专业词汇，不带代词、语气词和标点。

证据：列出全部 H2，逐个对照词表，指出不合规的。

**C15 没有重复**（§8）

同一个事实不在三处各讲一遍；同一条规则不在两份文件里各写一次。

证据：指出删掉了哪几处，或者说明为什么必须重复。

## D 安装与分支

**C16 安装路径一眼能定位**（§7）

共用安装器、差异只在目标参数时，按客户端分段，每段一条填好参数的完整命令，标题是客户端名；超过六个时把最常用的六个分段，其余收成一行取值清单并指向安装器的官方清单。标题不能是「方式一」「方式二」这种，那会让人以为有几种装法。安装器不支持的客户端单独一段，给原因和一条能复制的命令。

证据：从安装段标题到读者要复制的那条命令隔几行；命令里的参数值填没填好、能不能直接复制。分段与否写出客户端数量和判断；取值清单写出出处链接。

**C17 安装段正文不写目录、不写怎么调用**（§7）

正文里不出现安装目录，也不出现装完在宿主界面里按什么键。这两样是安装器的输出和读者的既有习惯。例外：安装器不支持的客户端，命令代码块里要写出它实际读取的目录，那是读者要复制的目标路径；正文仍不许解释「装到了哪里」。

证据：`check-text.py` 报的安装段命中；零命中就写「零命中」。脚本先剥掉代码围栏再判，所以命令里的路径不会命中；它也判不了目录之外的说法，比如「装在你习惯的位置」，那种要自己看。

**C18 每个分支都能走完**（§7）

需要什么 → 获取哪个包 → 在哪里执行 → 怎么确认装上了。命令里不留 `<repo-url>`、`<owner>/<repo>`、`<技能目录>` 这类占位符——读者照抄跑不通，等于没写安装。

证据：四个答案各对应哪一行；`check-text.py` 报的占位符命中；缺哪个写缺。

## E 双语

**C19 两版结构对应**（§7）

章节数、顺序、安装分支、限制、许可、帮助路径一致，不是一份完整加一份简介。

证据：脚本的对照结果。

**C20 事实不漂移**（§7）

命令、包名、参数、版本条件、URL 原样一致；不把有条件描述译成保证，不漏掉限制。

证据：至少三处贴出两边对应句。

## F 渲染与收口

**C21 两个脚本都跑过**（§8）

按绝对路径调用，不是照 `scripts/...` 直接敲。

证据：贴命令和输出。

**C22 渲染看过**（§8）

按下面三档之一检查，并写明用了哪一档：

1. **真实渲染**：目标平台的线上页面，或按同一套 CSS 复现的本地预览。
2. **静态估算**：按 838px 正文列、392px 表格单元格换算，核对图内最小字号、声明宽度和固有宽；`check-assets.py` 已经算完这一档能算的部分，剩下读 `<style>` 和窄屏媒体查询。
3. **纯源码**：只做结构和链接检查，明确写「未做渲染验收」。

第三档仍是缺口，不能当通过。降级是用来区分「没条件做」和「做了没过」，不是把缺口写成合格。

检查范围：首屏、安装、示例、文末，在常规宽度和约 390px 窄屏各看一遍。

- 一份文档只有一个 H1；H2/H3 语义清楚，锚点落点正确。
- 图片加载且关键内容可读；复杂截图在窄屏允许点开原图，不假装是可用界面。
- 浅色与深色两套主题下都能读，不出现刺眼白板或消失的文字。
- 长命令在代码区滚动，不撑出整页；表格不迫使读者横移才能读完每段说明。
- 实际点击语言切换、锚点、图片和折叠；必要内容没被 HTML 渲染吞掉。
- 没有靠任意 CSS 美化出一个在 GitHub 上不成立的排版。

证据：哪一档、看了哪些位置、发现什么。

**C23 交付说明写全**（§8）

关键变化、实际验证、剩余缺口，缺一项都不算完。

证据：交付时一并说明，不另建报告文件。

## G 逐段审查

这组查的是「读者能不能一下拿到点」，脚本判不了，只能逐节看。按 H2 一节一行记录；节内某一段答不出，单独列出来改，不拿整节的平均印象过关。

**C24 受众是状态不是身份**（§2）

不出现「面向开发者」「适合团队」「适用于各类项目」这类读者认领不了的说法。每节第一句要能让读者对号入座：他此刻卡在哪、要做成什么事。

证据：引每节第一句，写明它对着的是哪种状态。只有身份词、没有状态的，算不过。

**C25 每节答得出三问**（§8）

这节写给谁、他读完能复述什么、他读完会做什么。三问答不出的节，删或重写。

证据：H2 清单，每节一行写三个答案。答案里出现「了解」「认识」「感受」这类词，视作没答出来。

**C26 判断在前，理由最多一句**（§8）

每段第一句是结论，后面最多一句支撑。连续三句都在解释背景、动机、设计取舍的段落，标出来改。一段超过两句就删或拆成列表。

证据：逐段数句子（中文按句号、问号、叹号，英文按句点），每个 H2 下写「第几段：几句、第一句是判断还是铺垫」，至少三段贴原文。超过两句的段点名重写。只写「已精简」「已检查」不算过。

**C27 例子撑得住结论**（§8）

出现「改前 / 改后」「对比」「示范」时，下面几条都要有答案：

1. 改后确实比改前好，好在哪一步能指认——少几个分句、用途提到第几句、对象从哪挪到哪。
2. 改后丢了什么、丢的去哪了。挪走的内容写明了去处，不是凭空消失。
3. 不会让人读成另一件事；引用别人的公开提交时只做事实对照、不替对方下结论、旁边写明不是对方背书；引用截图、评价或未公开材料，才需要先取得同意。
4. 贴进正文的引文，在它旁边那个链接点开后能看到。写明文件名和位置；链接指向 README、引文却来自同一 commit 里别的文件，算不过。
5. 引文的语言跟着这一版的读者走：中文版引中文原文、链接中文文件，英文版引英文原文、链接英文文件。英文版里出现整段中文原句，或把译句当原文，算不过；两版共用一条链接也算不过。

证据：改前改后的原文各贴一句进正文，加「好在哪一步」的具体计量。只有「4 句减到 1 句」这种计量、不贴原句，读者仍看不出差在哪，算不过；只写「明显更清楚」同样不算。引用别的仓库时给能点开的链接（commit 或文件），只写「第 118 行」读者没法自己核。实际打开链接确认原句在那份文件里，把核对结果写出来。双语项目额外贴两版各自的引文和链接，写明各自的文件名与行号；英文版引文里不含中文原句。

**C28 砍一半还成立**（§8）

删掉解释、背景、「为什么这么设计」之后，这节剩下的仍然说得通。删完就空的段落，整段删掉，不留在正文里。定位句、图注、适用场景里的对照讲的是同一件事时，只留一处，不换种说法再讲一遍。

证据：列出删掉的原句；逐段写有没有重复首屏说过的话。只写「已精简」不算过。

**C29 每个点都是读者能拿走的一件事**（§5）

逐个 H2 下的每一条看一遍，不是只看第一节。功能/能力类的条目必须是「读者找它做的一件事」，不是它遵循的标准，也不是它纠正过的毛病：

- **任务**（写一份、改一份、只评审、出双语、发布前查一遍）→ 过。
- **标准**（三种形态、首屏四样、25 行、按类型挑证据、章节顺序）→ 不过。这些是方法，放示例里让它显形，或指向 `SKILL.md`。
- **症状**（「首屏堆满」「用形容词代替证据」）→ 不过。这是诊断，不进正文。

证据：每个 H2 下的条目数一遍，逐条写「读者会找它干的那件事」；写不出来或写成标准的，点名列出，改完再交。

**C30 没教读者做他本来就会的动作**（§7、§8）

「复制下面的命令在终端执行即可」「按你手上的系统选一段」「按提示操作」「照着做即可」这类句子，删掉不影响任何一个判断。执行位置并进前提那句，不单独成句。

证据：安装节逐句列一遍，写出删了哪几句；脚本命中即不过。

**C31 没有原稿也要对账**（§8）

从零写、或原稿被移走时，动笔前先列一张单子：安装依赖与系统下限、隐私与权限范围、已知限制、再分发条件、仓库里已有的证据图、CI 或构建脚本会从 README 读走的命令。成稿逐项对，留下的给行号，删掉的给去处（产品页、`docs/`、本页另一节）。既没留也没去处的补回去；「为了首页短一点」不算去处。

证据：对账单全文，每行带行号或链接；不适用的写原因。缺这张单子按未完成算。

**C32 Skill 类项目覆盖常见客户端**（§7）

README 给 Agent Skill 写、安装段用到 `npx skills add` 这类安装器时，先打开安装器支持的客户端清单（包内 `docs/agents.md` 或官方 supported agents 页），逐个核常见客户端：Claude Code、Codex、Cursor、OpenCode、Qoder、ZCode、Pi、Trae、Continue、OpenClaw、WorkBuddy 等，按项目受众挑。支持的写进分段或一行取值清单，`-a` 之类的值要和清单逐字一致，不许凭印象编；清单里没有的客户端单独一段写出「安装器不支持」，给一条能直接复制的命令把它实际读取的目录填实，并写明成功标志。只列两三个客户端，或给不支持的客户端编一个参数值，算不过。

证据：清单的文件路径或链接、每个 `-a` 值在清单里的位置、覆盖的客户端数、不支持客户端那条命令里的目标目录和成功标志。脚本只会在一个客户端都没交代时提示，逐值核对要自己做。

## 脚本能判什么

`check-assets.py` 判：图不存在、大小写不符、字号换算后过小、远程字体被 CSP 拦、缺 viewBox、超出正文列宽、Markdown 与 HTML 链接指向不存在的路径。

`check-text.py` 判：首屏行数、首屏有没有动作或证据、徽章数量、H1 数量、失效锚点、两版章节数、术语漂移、H2 是否写成口头语或拿去列仓库文件清单、版本与系统下限有没有出处、安装段有没有写安装目录和宿主调用步骤、安装段有没有「复制命令即可」这类零信息动作句、命令块里有没有留 `<...>` 占位符、正文有没有贴脚本输出、英文版引用块里有没有整段中文原文、Agent Skill 类项目的安装段是不是只列了一两个客户端。安装段的目录判据先剥掉代码围栏：命令里的目标路径不报，正文里解释装到哪才报。

**脚本通过不等于可以交付**：C5、C8、C10、C11、C22、C31、C32 它完全判不了；C9 和 C17 只认得出格式，认不出换了说法写进去的同类内容；C26 的句数脚本不数，要自己在验收表里逐段数。

换平台（GitLab、Bitbucket、npm、PyPI）要重新量列宽，用 `--column-width` / `--table-width` 覆盖脚本里的 GitHub 实测值。

## 有独立审阅者时

只给成稿和必要事实，要求对方复述用途、值得试的具体理由、各分支下一步和限制，并指出位置。反馈是待判断的建议：修真问题，调查缺证据项，合并重复，拒绝编造或越权。

## 收口

事实与操作门通过、渲染无阻断、读者能解释项目区别并完成对应路径，才可以交付。仍有未知分支、未渲染或未实测时，在交付说明里列出具体缺口；不用「测试通过」替代，也不用删掉用户需求来显得完成。

本 Skill 自身改动后的新旧版对照见[维护与回归](maintenance.md)。
