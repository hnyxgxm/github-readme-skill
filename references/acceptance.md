# 验收：这篇首页能不能用

判断标准是读者能否据此决定要不要试、并完成第一次使用。章节齐全、字数变少、链接全部通过、模型自评高分，都不能单独证明写得好。

## 怎么用这张清单

- 按编号顺序逐条回答，不许跳。
- 每条必须给证据：行号、引用原文、命令输出或文件路径。只写「已检查」「已符合」不算过。
- 不过的先改稿，再走下一条；确实不适用的写原因，不能拿「不适用」逃掉该做的条目。
- 交付时附报告表。缺表按未完成算，不按「基本做完」算。

报告表长这样，一行一条：

| 编号 | 结果 | 证据 |
| --- | --- | --- |
| C3 | 过 | 第 1 行标题，第 3 行徽章，第 6 行定位，第 11 行图 |
| C11 | 不过，已改 | 版本 22.20 在仓库里查不到出处，补了 `package.json` 的 `>=22.20.0` |

口径以 SKILL.md 为准。本页只列检查项和证据要求，不重复那里的数字与规则。

## A 形态与范围

**C1 形态判对了**（§1）

路由页、中间态、手册三选一，判据是有没有独立文档站或仓库内文档目录，不是正文里恰好有没有链接。

证据：写出判定，并列出仓库里支持这个判定的路径。

**C2 范围和语言都在授权内**（§2）

只改说好的范围；不改产品、许可、发布渠道或远端状态。

证据：改了哪些文件；为什么是这几版语言。

## B 首屏

**C3 四件套齐**（§4）

身份、一句定位、信任标记、第一次结果，缺一件就不过。

证据：四件各在第几行。

**C4 长度没超**（§4）

首屏控制在规定行数内。

证据：脚本报的首屏行数，不自己数。

**C5 第一次结果是读者想要的**（§5）

照这一步做完拿到的东西，是他本来就需要的结果，不是「能跑」的证明。

证据：引一句，说明这步做完拿到什么，为什么读者本来要这个。`hello world`、版本号、`--help` 输出都算没过。

**C6 信任标记有用**（§4）

徽章不超过上限，每个都能帮判断；一个都没有时用出处或赞助信息顶上，不是纯装饰墙。

证据：逐个说这个徽章让读者知道什么。

**C7 图注只说看什么**（§4、§6）

图注说明这是什么、该看哪里，不替读者下结论，也不用否定句补救。

证据：引用图注原文。

## C 内容与证据

**C8 主证据对得上交付物**（§5）

按交付物选证据，一份主证据放在首屏附近，其余按功能分置。

证据：主证据是什么、在第几行、能证明到什么程度。

**C9 诊断没进正文**（§8）

脚本输出、检查清单、修改记录、写作说明是修稿用的输入。读者要看的是成品。

证据：`check-text.py` 的输出行检查零命中；再搜 `检查`、`已修改`、`诊断`、`修复了` 这类叙述，确认没把修稿过程写进去。

**C10 差异是两种做法的对照**（§5）

写成以前怎么干、现在怎么干，不用「更快、更优雅」这类比较级；引用的数字带环境说明和出处。

证据：引用那一段。

**C11 写了什么时候别用它**（§5）

不适用场景、平台与权限限制、成熟度，至少一句。全篇只夸按未完成算。

证据：行号加原文。

**C12 事实都有出处**（§3）

版本、命令、平台、许可、下载量，都能在仓库文件或官方文档里对上。

证据：脚本的版本核对结果，加上逐条对应关系。

**C13 没有仓库文件清单**（§5、§6）

没有「目录」「仓库结构」「项目结构」这类 H2，也没有文件树和逐文件说明。

证据：列出全部 H2。

**C14 章节名在词表内**（§6）

H2 只用通用专业词汇，不带代词、语气词和标点。

证据：列出全部 H2，逐个对照词表，指出不合规的。

**C15 没有重复**（§8）

同一个事实不在三处各讲一遍；同一条规则不在两份文件里各写一次。

证据：指出删掉了哪几处，或者说明为什么必须重复。

## D 安装与分支

**C16 只有一条命令**（§7）

多个客户端共用安装器时，不按客户端拆成多段，差异收在一个参数位。

证据：行号。

**C17 安装段不写目录、不写怎么调用**（§7）

不出现安装目录，也不出现装完在宿主界面里按什么键。这两样是安装器的输出和读者的既有习惯。

证据：`check-text.py` 报的安装段命中；零命中就写「零命中」。它也判不了目录之外的说法，比如「装在你习惯的位置」，那种要自己看。

**C18 每个分支都能走完**（§7）

需要什么 → 获取哪个包 → 在哪里执行 → 怎么确认装上了。

证据：四个答案各对应哪一行；缺哪个写缺。

## E 双语

**C19 两版结构对应**（§7）

章节数、顺序、安装分支、限制、许可、帮助路径一致，不是一份完整加一份简介。

证据：脚本的对照结果。

**C20 事实不漂移**（§7）

命令、包名、参数、版本条件、URL 原样一致；不把有条件描述译成保证，不漏掉限制。

证据：至少三处贴出两边对应句。

## F 渲染与收口

**C21 两个脚本都跑过**（§8）

按绝对路径调用，不是照 `scripts/...` 直接敲。

证据：贴命令和输出。

**C22 渲染看过**（§8）

按下面三档之一检查，并写明用了哪一档：

1. **真实渲染**：目标平台的线上页面，或按同一套 CSS 复现的本地预览。
2. **静态估算**：按 838px 正文列、392px 表格单元格换算，核对图内最小字号、声明宽度和固有宽；`check-assets.py` 已经算完这一档能算的部分，剩下读 `<style>` 和窄屏媒体查询。
3. **纯源码**：只做结构和链接检查，明确写「未做渲染验收」。

第三档仍是缺口，不能当通过。降级是用来区分「没条件做」和「做了没过」，不是把缺口写成合格。

检查范围：首屏、安装、示例、文末，在常规宽度和约 390px 窄屏各看一遍。

- 一份文档只有一个 H1；H2/H3 语义清楚，锚点落点正确。
- 图片加载且关键内容可读；复杂截图在窄屏允许点开原图，不假装是可用界面。
- 浅色与深色两套主题下都能读，不出现刺眼白板或消失的文字。
- 长命令在代码区滚动，不撑出整页；表格不迫使读者横移才能读完每段说明。
- 实际点击语言切换、锚点、图片和折叠；必要内容没被 HTML 渲染吞掉。
- 没有靠任意 CSS 美化出一个在 GitHub 上不成立的排版。

证据：哪一档、看了哪些位置、发现什么。

**C23 交付说明写全**（§8）

关键变化、实际验证、剩余缺口，缺一项都不算完。

证据：交付时一并说明，不另建报告文件。

## 脚本能判什么

`check-assets.py` 判：图不存在、大小写不符、字号换算后过小、远程字体被 CSP 拦、缺 viewBox、超出正文列宽、Markdown 与 HTML 链接指向不存在的路径。

`check-text.py` 判：首屏行数、首屏有没有动作或证据、徽章数量、H1 数量、失效锚点、两版章节数、术语漂移、H2 是否写成口头语或拿去列仓库文件清单、版本与系统下限有没有出处、安装段有没有写安装目录和宿主调用步骤、正文有没有贴脚本输出。

**脚本通过不等于可以交付**：C5、C8、C10、C11、C22 它完全判不了；C9 和 C17 只认得出格式，认不出换了说法写进去的同类内容。

换平台（GitLab、Bitbucket、npm、PyPI）要重新量列宽，用 `--column-width` / `--table-width` 覆盖脚本里的 GitHub 实测值。

## 有独立审阅者时

只给成稿和必要事实，要求对方复述用途、值得试的具体理由、各分支下一步和限制，并指出位置。反馈是待判断的建议：修真问题，调查缺证据项，合并重复，拒绝编造或越权。

## 收口

事实与操作门通过、渲染无阻断、读者能解释项目区别并完成对应路径，才可以交付。仍有未知分支、未渲染或未实测时，在交付说明里列出具体缺口；不用「测试通过」替代，也不用删掉用户需求来显得完成。
