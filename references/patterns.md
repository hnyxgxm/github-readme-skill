# 结构、版式与编辑示范

借鉴的是读者路径，不是皮肤。下面的正向规范是本 Skill 的编辑约定，并非 GitHub 强制格式；按项目规模和宿主渲染结果调整。具体项目的取舍见[范例清单](examples.md)。

## 先选形态

判据、篇幅和职责在 `SKILL.md` §1，本节只讲三种形态读起来差在哪、通常怎么选错：

| 形态 | 读者读起来什么样 | 常见的选错方式 |
| --- | --- | --- |
| 路由页 | 首屏就能决定要不要看，点两下到文档站；本页只留定位、一行入口、文档链接、许可 | 把文档站的安装和参数抄回来，两处维护，先烂的是 README |
| 中间态 | 首屏、安装、最小用法留在本页，长内容链进 `docs/`；不读文档也能试一次 | 只链不写，读者点进 `docs/` 仍不知道从哪篇开始 |
| 手册 | 安装、用法、参数、边界、常见问题都自带，读完不必再找别处 | 缩成路由页，读者无处可去，只能去读源码 |

## 先选形状

形状的判断口径在 `SKILL.md` §6，这里只列三种最常犯的错形，供落笔时对照：

- **长说明塞进表格**：单元格变成第二篇草稿，读者来回横移。解释回段落，表格只留可比的短项。
- **因果链拆成列表**：每条都对，读者拼不出为什么。链条回段落，列表只留同类并列。
- **文字能说清的事硬配截图**：图证明不了区别，就是装饰。先问这张图证明什么，答不出就删。

## 从真实首页提取方法

2026-10-29 读了 14 个不同类型的完整 README，清单与 star 数见[范例清单](examples.md)。四种可重复的做法：

- **uv**：一句“极快”后立刻跟基准图和说明文字，Highlights 每条带锚点，安装在第 2 节。承诺 → 证据 → 上手，中间没有形容词。
- **ripgrep**：参考型长文把安装排到正文很靠后，但首屏 quick links 第一个就是 Installation；另设 Why shouldn't I use ripgrep?，把不适用场景写清楚。
- **lazygit**：Elevator Pitch 用第一人称讲痛点，Features 每条一个 H3 + 动图，Alternatives 单独成节。
- **shadcn/ui、zed、transformers**：有文档站时 README 只做路由器（17、48、74 行），安装、平台可用性和文档入口留在首屏。

共同点：首屏永远短，长的是首屏以下的参考；证据类型跟着交付物走；同一件事不讲三遍。

## 七类骨架

每类给出最小章节顺序，可合并或省略；证据怎么选见下一节。

### CLI / TUI

`名称 → 一句 → 安装一条命令 → 演示（基准表 / 录屏 / 动图） → 用法 → 为什么或对比 → 文档 → 贡献 / 许可`

- 安装通常在第 1–3 节；排得更后时，首屏 quick links 必须给跳转。
- 基准带环境（CPU、版本、命令）；录屏 10 秒内，展示真实输入与输出。
- 参考：uv、ripgrep、lazygit、simonw/llm。

### 库 / SDK / 框架

`名称或 logo → 定位 → 安装 → 最小调用与输出 → 特性（每条带文档链接） → 文档 → 生态 → 许可`

- 最小示例就是价值证明：真实输入、真实返回、必要的类型或错误处理。
- 特性 3–7 条；文档站存在时只留最有区分度的，其余链走。
- 参考：zod、fastapi。

### 桌面 / Web App

`logo → 定位 → 下载或在线入口 → 界面证据 → 特性 → 从源码构建（后置） → 社区 → 许可`

- 平台可用性写全：支持哪些、哪些还没有、去哪跟踪。
- 图要可读；窄屏允许点开原图，但不假装是可交互界面。
- 参考：zed、excalidraw。

### SaaS / 平台

`logo → 一句 → 能力清单（每项带 Docs 链接） → 产品截图 → 文档 / 社区 → 架构说明`

- 托管服务的入口是文档站或注册页，不编造本地安装。
- 社区渠道写清用途（Bug、搭建求助、商务支持），不只堆链接。
- 参考：supabase。

### 研究 / 模型 / 数据集

`名称 → 带数字的主张 → 安装 → quick start → 复现与基准表 → 权重或数据来源 → 引用 → 许可`

- 用规模、硬件、耗时代替“强大”；结果表标环境与评测集。
- 状态要显眼：预览、弃用、后继项目。
- 参考：nanoGPT、llama.cpp、transformers。

### Agent Skill

`名称 → 一句 → 支持客户端 → 按客户端分段的安装命令 → 首个任务 → 示例 → 边界 → 许可`

- 每段标题写客户端名，命令里的参数值填全；超过四个客户端改回一条命令加交互提示。实验特性折叠；不同渠道不并列成清单。
- 示例给真实任务的输入与产出，不用效果对比暗示模型提升。
- 参考：vercel-labs/skills。

### 模板 / 脚手架

`名称 → 一句 → 一分钟初始化 → 目录结构（只讲要改的地方） → 采用后的产物 → 许可`

- 目录树只列读者会动的文件，不搬全部源码结构。

## 首屏的编排

依次让读者辨认名称、语言、用途、主要行动和证据。语言导航可紧邻标题上方或下方，两种语言位置一致；用途与主要入口不要被大图压到数屏之外。

首屏行数与徽章个数的口径以 SKILL.md §4 为唯一出处，本节讲怎么写，不重复数字。

- **名称**：一个 H1，保留项目名；已有 Logo 是身份材料，不再制造重复的装饰大标题。
- **定位**：普通正文一到两句，先说具体任务和得到什么，再说必要机制。不要整段加粗来代替写短。
- **信任**：功能性徽章，个数按 §4，或出处、赞助信息；每个都要帮助判断。
- **第一次结果**：一条现在就能做的动作，加做完拿到的东西。给读者本来想要的那个输出，不给“能跑”的证明；只写安装命令等于让他先赌一次。
- **导航**：H2 超过 6 个或安装排在第 4 节之后，才在首屏加 quick links 或 TOC；只列 H2，不列每个 H3。
- **图注**：说明“这是什么、看什么”，通常一两句，默认普通正文。“教学示范”“原型”这类身份词比一串否定声明有效。

首屏长度按 §4 控制。若首次动作必须跨过重复价值介绍、发布流水账和长篇限制，优先移除阻碍，而不是把字体缩小。

### 反例与改写：同一张图，不同的阅读负担

反例：长段全粗体定位，接一段全斜体的截图生成过程、工具版本及多项“不是……”声明。

改写示意（图已核实为教学示范，不是效果实验）：

```markdown
# UI Taste Skill

[English](README.en.md) · 简体中文

让 AI 编程助手先确定界面方向，再把布局、排印与交互做完整。

[安装](#安装) · [使用](#使用) · [示例](#示例)

![同一组六份字体标本组成的展陈界面](assets/reference-evidence/studio-gallery-desktop.png)

「字间」教学示范：同一组内容的展陈方向。另见[工作面方向](assets/reference-evidence/studio-instrument-desktop.png)。
```

这是首屏片段，不是完整模板；后文不得暗示教学图证明模型效果提升。

### 第一次结果：给结果，不给“跑通了”

同一件事的两种写法。下面都是示意，真实输出按项目替换。

反例：读者照做，拿到一个他不需要的结果。

```sh
npm i -g some-tool && some-tool --version
```

```text
some-tool 1.4.2
```

改写：接一件他本来就想干的事，输出本身有用。

```sh
some-tool ./slides --out demo.mp4
```

```text
读取 slides/ 下 6 页 Markdown，1920x1080，30fps
demo.mp4  8.4 MB  00:12
```

装完就验版本号，等于让读者自己想象这工具能干什么；给一次真会用到的事，他当场能判断值不值得留。Skill 类同理：装完之后的第一条不是 `/help`，是一次真实触发，附上它改了哪个文件、改成了什么。输入与输出分开放，读者复制命令时不会把结果一起带走。

完整的第一次结果包含四件事：在哪执行、要准备什么、命令或操作、成功的标志长什么样。缺其中一件时，读者会在半路停下来猜。

## 证据矩阵

主证据和第一次结果按 `SKILL.md` §5 定，本表只补它没写的两件事：放哪、容易错在哪。

| 交付物 | 放哪 | 常见错误 |
| --- | --- | --- |
| CLI | 首屏下方 | 无环境说明的跑分；命令没有输出 |
| TUI / 桌面 App | 首屏 | 缩到不可读；展示并不存在的状态 |
| 库 / SDK | 首屏或第 2 节 | 示例缺依赖或版本；只贴 API 签名 |
| Web / SaaS | 首屏 | 仓库内 HTML 冒充在线体验 |
| 研究 / 模型 | 首屏与复现节 | 无环境的结果；权重无出处 |
| Agent Skill | 首屏与示例节 | 教学图被读成效果证明 |
| 模板 | 首屏 | 只给目录树，看不到成品 |

一份主证据放在首屏附近；其余按功能分置。证据不足时缩窄承诺，不用形容词补位。

## 强调与引用

`SKILL.md` §6 管层次和形状，这里只补它没规定的三件小事：

- **能力用短标签加行为说明**：「**按原稿还原**：保留构图和排印，不擅自添加装饰」。标签形成扫读骨架，不把每句话都加粗。
- **引用块用于引用或提醒**，不包住整篇宣传文案；分隔线只在确有转折时用。
- **自然语言任务按语义拆短行**，但不要为此折断一条可执行命令。

## 安装：按客户端分段

渠道选择、每类读者要走完的四步、核实口径都在 `SKILL.md` §7。这里只给形状。

同一个安装器、差异只在目标参数时，先数客户端。四个以内按客户端分段，每段一个客户端名加一条填好参数的完整命令，读者只读自己那段：

````markdown
**Claude Code**

```sh
npx skills add <owner>/<repo> -g -a claude-code
```

**Codex**

```sh
npx skills add <owner>/<repo> -g -a codex
```
````

超过四个就反过来：一条命令加一句"终端会让你选"，不列参数表。段标题写客户端名，不写"方式一""方式二"——后者才让人以为有几种装法。

不写这些：每段后面的安装目录、装完在宿主里按哪个键、`$<技能名>` 与 `/<技能名>` 的调用差异。目录是安装器自己打出来的，调用是读者的既有习惯，两样都会随客户端升级过期；参数值写全是为了让读者不必回头查，不是为了把同一个动作讲三遍。

真实写法见本仓库 README 的安装段——版本条件、参数值只有那一处是准的，示例里不复制具体值。

## 能力段与边界

写法按 `SKILL.md` §5，这里只补示范。

能力段里"项目名替换后仍适用于任何项目"的句子，一律改成具体行为，不枚举技术名词，不用"强大、优雅、先进"。

**条目写读者找它干的那件事，不写标准和毛病。** 两种最常见的写错，作者自己都看不出来：

```markdown
<!-- 不算功能：写成了标准（读者读完知道你讲究，仍不知道该拿你干什么） -->
- **该写多长的判据**：有独立文档站做路由页，有 docs/ 做中间态，都没有做手册。
- **首屏该放的四样**：身份、一句定位、一个可核的标记、第一次能拿到的结果，25 行内。

<!-- 不算功能：写成了症状（读者既没承认过也听不懂） -->
- **首屏堆满**：首屏只放四样，压在 25 行内。
- **用形容词代替证据**：按交付物挑主证据，不为了有图硬放一张图。

<!-- 是功能：读者找它做的一件事 -->
- **从零写一份**：给它仓库路径，它先定形态、列结构方案，你确认了再写全文。
- **把现有的一份改好**：先说清哪节顺序不对、哪段该换成证据，出对照，你认可了再动笔。
```

标准和症状的去处不同：标准放进「示例」，让改前改后自己显形；症状哪里都不进。判据一句话：把这条单独摘出来给陌生人看，他能不能说出「我可以找它干这件事」。

对照要写成两种做法，不写比较级：

```markdown
以前：打开终端，翻到 ~/Library/Developer/Xcode，逐个子目录看体积，删完还要去废纸篓找回误删的
现在：扫完按体积排序，勾选删除，误删从废纸篓还原
```

判断标准一句话：这段话里有没有出现读者上周真做过的那件事。出现了，他对号入座；只出现产品名和形容词，他就划过去了。数字要带环境，比如"12 万文件下 0.08 秒"，没有环境和命令的跑分不如不写。

边界同样值得写，成熟项目都敢写：

- **不适用场景**：ripgrep 专设 Why shouldn't I use ripgrep?，说明什么时候该换工具。
- **与替代的差异**：lazygit 单列 Alternatives，比较的是工作方式，不贬低对方。
- **状态与成熟度**：预览、实验、弃用要显眼；nanoGPT 在首屏直接指向后继项目。

学的是内容不是标题形式：这三个例子各自开了新标题，本 Skill 要求把它们并进「功能」或「适用场景」，不为它新造 H2。只写已核实的差异；没有比较数据就写"未验证"，不编造胜出结论。

## 中英双语：两份入口，不是两倍噪声

文件命名、同步范围和事实一致性按 `SKILL.md` §7，本节只留两处它没展开的细节：

- **三种语言导航各有出处**：双文件互链（两版顶部各一行）、顶部语言条（transformers）、底部 Translations 列表（ripgrep、supabase）。按规模选一种，两版位置一致。
- **菜单名按宿主真实显示保留**，不凭空翻译成不存在的按钮；README 有英文不等于软件或截图已英文化。

## 另一个完整形态：没有图的短工具

假设读者已取得源码，以下是一个仅供中文团队使用、未发布 Python 小工具的完整示例：

````markdown
# csv-sum

读取 CSV 的指定数值列并输出合计，不修改原文件。

## 使用

需要 Python 3.10+，无需第三方依赖。在解压后的源码根目录运行：

```sh
python3 csv_sum.py samples/orders.csv --column amount
```

示例输出：

```text
42.50
```

将 `samples/orders.csv` 换成自己的文件，`amount` 换成要合计的列名；文件路径含空格时用双引号括起。
````

它不需要语言导航、主图、徽章、卖点表或“安装”空章节。输入没有异常数据规则时，不凭经验补“自动忽略无效行”。没有包索引就不写 `pip install csv-sum`。没有许可证不代表可自由再分发；纯内部使用说明不必硬加章节，公开分发前先请权利人确认授权。

仓库内文档已经够用时，README 可以只做路由器（示意）：

````markdown
# northwind-ui

面向内部后台的 React 组件集，默认支持深浅色与键盘操作。

## 文档

组件清单、设计约定与变更记录见 `docs/`。

## 安装

```sh
pnpm add @northwind/ui
```

## 贡献与许可

见 `CONTRIBUTING.md`；MIT。
````

## 对反馈做编辑，而非逐句服从

- “再强调高级、强大” → 补具体任务和可观察的区别，而非添加形容词。
- “补上所有测试数字” → 保留影响采用的证据，其余移到已有维护入口。
- “写成纯人工设计” → 无制作记录就不采纳；不能为消除一种误解而制造另一种。
- “看起来专业一点” → 先修定位、层级、分流和示例，再检查有限的品牌材料，不默认加徽章墙。
- “更短” → 删除重复叙述，不删环境、首次操作或数据风险。
- “把旧内容都留着” → 保留必要事实，允许合并和重组旧句；不要把首页写成修改意见的回复串。
