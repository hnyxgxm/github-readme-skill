# 项目分类表与读者分析

第 2、3 步用这份。它回答两件事：**这个项目属于哪一类**、**谁来读、他来干什么**。

分类不是为了给项目贴标签，是为了少走弯路：同类项目，读者第一步要做的事往往一样，首屏能拿出手的证据也差不多。所以分类结果必须直接接到段落骨架上。

## 一、五类项目

先看 `detect_project.py` 输出的字段，再对照下表选一行。理由里要能点到具体文件，例如「有 `pyproject.toml` 的 `[project.scripts]`，没有 `docs/`」；只说「感觉像工具」不算判断。

### 1. 工具类：命令行、桌面软件

| 项 | 内容 |
| --- | --- |
| 文件线索 | `package.json` 的 `bin`、`pyproject.toml` 的 `[project.scripts]`、`Cargo.toml` 的 `[[bin]]`、`go.mod` 里有 `cmd/`、有可执行文件或安装包 |
| 读者第一件事 | 装好，跑通一条命令，看见预期输出 |
| 第一段 | 用它替掉哪一步手工操作；一句话说清输入什么、得到什么 |
| 主证据 | 一条真实命令加输出，或一张能看清的界面截图 |
| 第一次结果 | 复制命令 → 看到输出 → 知道成功长什么样 |
| 常见错法 | 把全部参数、配置文件、环境变量搬进首页；把安装埋在「功能特性」后面；拿 Logo 当证据 |

命令行和桌面软件在这份表里同类，但证据不一样：命令行用文字输出，桌面软件用界面图。别给命令行硬造截图，也别给桌面软件只贴一段日志。

### 2. 教程或方法类

| 项 | 内容 |
| --- | --- |
| 文件线索 | 主要内容是 Markdown、笔记、课程目录、`examples/`、`chapters/`；没有可安装的程序入口 |
| 读者第一件事 | 找到适合自己当前水平的那一节，跟着做完一小段 |
| 第一段 | 学完能做出什么；适合谁、不适合谁；大概要花多少准备 |
| 主证据 | 目录结构、一个完整例子、学完之后拿得到的产物 |
| 第一次结果 | 打开第一节，跟着做出一个能看见的东西 |
| 常见错法 | 写成课程宣传页，满是「系统全面」「深入浅出」；不写前置要求，读者点进去才发现跟不上；把整本书的目录原样贴一遍 |

这一类最容易缺「不适合谁」。写清楚比多列十章目录有用。

### 3. 网站或在线服务

| 项 | 内容 |
| --- | --- |
| 文件线索 | 有前端目录、构建配置、部署配置（`vercel.json`、`netlify.toml`、Dockerfile）、线上地址 |
| 读者第一件事 | 打开站点，完成一次能看见的操作；或者按说明自己起一份 |
| 第一段 | 打开能干什么，为谁解决哪件事 |
| 主证据 | 真实界面截图，或能直接点开的在线入口 |
| 第一次结果 | 打开 → 操作一次 → 看到结果 |
| 常见错法 | 首屏全是技术栈徽章，没有一张界面；把「本地起服务」的十几步写在「在线试用」前面；截图是开发环境的调试页面 |

有线上地址就把它放在第三段最前面。没有线上地址，如实写自托管步骤，不要把源码里的 HTML 文件叫「在线体验」。

### 4. 库或开发包

| 项 | 内容 |
| --- | --- |
| 文件线索 | `package.json` / `pyproject.toml` / `Cargo.toml` / `go.mod` 里有包名和对外接口，被别的项目引用；包管理平台上有发布物 |
| 读者第一件事 | 装进自己的项目，跑通最小调用 |
| 第一段 | 引入它解决哪个具体问题，别的项目为什么需要它 |
| 主证据 | 一段最小调用代码，加它的输出或结果 |
| 第一次结果 | 装包 → 复制示例 → 跑通 |
| 常见错法 | 第一段讲实现原理；示例要读者先配好三样东西才能跑；把完整接口表铺在首页；不写在哪个语言、哪个版本下可用 |

「最小」是硬要求：示例里每多一个依赖，读者跑通的概率就掉一截。

### 5. 其他：模板、研究、Agent Skill

| 项 | 内容 |
| --- | --- |
| 文件线索 | 以上四类都对不上；常见的是模板仓库、论文复现、数据集、技能包、配置集合 |
| 读者第一件事 | 复制 / 初始化 / 加载它，然后完成一次修改或复现 |
| 第一段 | 直接说清交付物是什么，别用「解决方案」「一站式」这类词绕 |
| 主证据 | 采用之后实际产出的东西，或复现命令与结果 |
| 第一次结果 | 拿到一份能改的副本，或跑出一组能对上的数字 |
| 常见错法 | 把研究写成产品介绍；拿效果图冒充复现结果；不写数据、权重、环境从哪来 |

这一类差异最大，五类表里最不该硬套骨架。拿不准就按第 3 步的「读者第一件事」自己排段落，并在六行结论里写明为什么没用现成骨架。

### 表外情况

真的对不上，就在六行结论第一行写「不落入任何一类」，再补两句：交付物是什么、读者第一步干什么。然后按 `section-templates.md` 的通用骨架写。**不要挑一个最接近的类别凑合**——凑合出来的类别会带着一整套不合适的段落，比不分类更糟。

### 一个项目像两类时

按「读者第一次要动手做的事」选，不按项目用了什么技术选：

- 一个命令行工具同时带教程 → 看首页主要想让人「装了就用」还是「跟着学」。前者选工具类，教程单独链出去。
- 一个库同时带在线演示站 → 通常选库，因为来仓库的人多半是要装包；在线地址放第三段当第二条路。
- 既是模板又是工具 → 选读者先做的那件事，另一件放到第五段。

## 二、读者分析

### 三类角色

| 角色 | 他来干什么 | 首页要给他什么 | 用词 |
| --- | --- | --- | --- |
| 直接用成品的人 | 装上、打开、做一次 | 一条能复制的命令、能看见的结果 | 少讲原理，说清「做完会得到什么」 |
| 要在上面开发的人 | 接进自己的代码、看懂依赖和版本 | 最小调用、版本条件、平台限制 | 可以出现术语，但每个都要能查到 |
| 要来贡献的人 | 知道从哪下手、规矩是什么 | 文档入口、反馈渠道、贡献说明 | 放最后一段，不占首屏 |

用户口头说的「技术人员 / 普通人 / 其他」可以当参考，但别拿它直接定结构：一个不懂代码的运营，来用命令行工具就是「直接用成品的人」；一个资深工程师，来学一门方法就是「跟着做的人」。**决定用词的是他来干什么，不是他懂多少。**

### 只选一个主要读者

六行结论里「主要读者」只填一个。次要读者可以列，但他们的内容放到后面段落：

- 主要读者是使用者 → 第一段到第四段都服务他；开发细节进第五段或链接出去；贡献放第六段。
- 主要读者是开发者 → 第一段就要说清「接到什么里、解决什么问题」；安装可以放第二段；界面图让位给调用示例。
- 主要读者是贡献者（少见，多为内部项目）→ 首屏说清项目在做什么、当前缺什么，环境搭建提前。

把三类读者平均写在第一段，结果通常是三段谁都看不懂的套话。

### 读者和语言

面向国际开源读者且有中文读者时写中英两版（`README.md` + `README.en.md`，顶部互链），结构和事实先定稿再写另一版。中文内部工具、单语读者、局部修订不强加双语。保留已有根 README 的语言和命名。

## 三、六行结论怎么填（实例）

拿一个真实的命令行项目举例，第 1 步脚本读到：`pyproject.toml` 有 `[project.scripts]`、有 `LICENSE`、`.github/workflows/` 下有一个检查配置、没有 `docs/`、没有图片、`README.md` 现有 12 行。

```
项目类别：工具类（命令行）
  理由：pyproject.toml 的 [project.scripts] 有入口；没有 docs/ 和图片，属于自带全部说明的手册型
主要读者：直接用成品的人
  他第一件事：装好，跑一条命令看到输出
  次要读者：要来贡献的人（放最后一段）
段落顺序：定位+徽章 → 命令与输出 → 第一步 → 做完第一步 → 还能提供什么 → 适用与去处
  标题：第三段按「装好，跑一条命令」取名「安装」；其余各段按 SKILL.md 第 4 节当场定，不照抄模板
主证据：一条真实命令的输出；项目里现在没有图，第二段用文字块，并告诉用户缺一张可读截图
图片与视频：不放。没有界面，静止图说不出额外信息；也不放装饰图
语言与范围：只写中文；只改 README.md，不动代码
```

注意两处：没图就写「缺」，而不是找一张凑上；类别理由点到了具体文件的具体字段。这样事后回头看，能查出来当初是按什么做的决定。

## 四、这一步最容易出的三种错

1. **先写后分类**：写完首屏才回头补六行结论，分类变成给已成稿的文字找理由。顺序反了，整份文档的价值就没了。
2. **拿技术栈当类别**：看见 React 就判「网站类」，其实那可能是一个给别的网站用的组件库。看文件线索和读者动作，别看技术名词。
3. **理由写不出文件**：「因为它是个工具」这种结论核不了。第 1 步的脚本输出就是用来给理由兜底的。
